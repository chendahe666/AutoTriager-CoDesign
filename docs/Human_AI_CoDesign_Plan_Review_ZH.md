# AutoTriager：Human–AI Co-Design 执行计划与审查

状态：计划稿，尚未实施。依据：9 月 21 日作业原文、已有 AI Design 材料、用户确认的设计，以及本次只读检查的 GitHub 默认分支。

## 1. 审查结论

方向与课程要求一致，但目前不能作为“已完成应用”提交。GitHub 的 AutoTriager 默认分支仅发现 README，没有已发布的 Streamlit 源码、依赖或测试。已有 AI Design 也明确写着原始数据加载及模型运行待验证。本次未检查其他本地项目目录、其他分支或其他开发环境，因此不据此断言所有地方都没有实现。

必须先纠正三个问题：

1. GitHub README 仍围绕 PR 归因、RCAEval 和 Online Boutique；本轮已选方向是基于 OpenRCA 的运行时故障分析。实现阶段应更新 README，区分本次交付与远期设想，撤下本轮不适用的准确率、成本和延迟目标。
2. 旧 AI Design 允许先交命令行或报告、界面后做；本次作业要求 Streamlit 应用可供审查。基础界面、人类核查和实际截图必须进入本次最小交付。
3. Bank 数据、EviRCA 适配器、可用模型及证据追溯能力尚未跑通。它们是需要验证的技术前提，不能作为已完成能力写进 PPT。

9 月 21 日提交已要求工作应用与仓库可供审查；9 月 30 日是最终报告截止时间，不能把全部实现推迟到那一天。本计划按依赖和退出条件组织，不承诺尚未验证的完成工时。

## 2. 本次唯一核心任务

用户选择一个离线故障案例，系统读取对应运行记录，运行已有分析方法，展示候选组件、可能原因、证据及信息缺口；用户打开原始证据，记录接受、拒绝或待核查的判断及理由。

延续原先第一个 P1：“加载选定系统的故障案例，并调用已有算法完成分析”。本次在它外面补上最小 Streamlit 界面和人类核查闭环，属于交付边界的必要完善。

本轮范围：一个系统、少量实际故障案例、一个分析调用路径、一个基础页面。Bank 是优先检查对象，只有数据和适配能运行后才冻结选择。

本轮不承担：PR 归因、在线生产接入、自动恢复、多个系统、复杂调用图、开放式聊天、跨历史案例检索、多 Agent 编排、效果提升承诺。复杂组件比较和连续追问仍留作后续功能。缺数据时说明局限属于基础行为，系统性的缺失数据鲁棒性实验仍是后续范围。

## 3. 人和 AI 怎样合作

| 步骤 | 用户操作 | 系统职责 | 用户得到什么 |
|---|---|---|---|
| 选择 | 选择案例并确认调查窗口 | 展示系统、时间范围和可用信号 | 明确本次在查什么 |
| 分析 | 点击分析 | 读取与检查数据，调用已有方法和模型 | 明确的运行状态 |
| 查看 | 阅读候选组件、原因和缺口 | 将每项观察连接到对应证据 | 有出处的诊断建议 |
| 核查 | 打开证据，核对原始记录 | 展示文件、行或 span 标识、组件、时间和计算方法 | 可以核查的依据 |
| 判断 | 接受、拒绝或标记待核查，填写理由 | 在当前会话保留判断及对应的分析版本 | 可见的人类审查结果 |

重新分析或切换案例时，不能把旧反馈误关联到新结果。当前会话反馈是本次基本交互，不等于已经实现长期历史管理。用户接受结果也不等于结果客观正确，不把反馈自动变成标准答案或模型训练数据。

老师允许多种人类核查方式，至少一种即可。这里选择“检查证据＋记录判断”，因为它直接服务于当前任务，且比完整追问系统更可控。

## 4. 最小架构与复用边界

Streamlit → 案例加载与输入校验 → 现有算法的处理／取证／分析流程 → 输出适配与引用检查 → 结果和证据展示 → 人类核查。

- Python 和已有工具完成时间归一化、数值处理及记录筛选。
- 按组件、时间和来源标识取证；有需要才保留现有图关系检索。不为了覆盖术语而添加向量数据库。
- LLM 对已获得的证据进行解释或比较，不自行计算统计量，不访问答案文件。
- 若现有算法已经包含模型调用和检索，直接封装其接口，避免再套一层功能相同的 Agent。
- 不强制新建 SQLite。先检查已有实现是否足够；少量案例可使用现有对象结构或文件索引。
- 每条证据保留稳定的来源指针；基本验证检查指针存在、范围和类型正确。证据是否真正支持诊断仍需人工审查。
- EviRCA 是复用候选，不是已验证可直接接入的依赖。先检查许可证、版本、环境、适配器、输出结构及原始记录追溯方式，再决定集成方式。
- 若修改原算法的默认补全或输出格式，应记录修改；不得把适配后的结果称为原论文完整复现。需要对比时保存未修改版本及配置。

## 5. 实施顺序与退出条件

| 阶段 | 具体工作 | 完成后必须留下的证据 | 未通过时怎样处理 |
|---|---|---|---|
| A. 数据与方法可运行性 | 读取一个真实案例和所需参考时段；检查现有算法输入；确认 API 或本地模型可用 | 数据清单、字段／单位检查、版本及一次真实调用记录 | 说明缺口并调整数据或方法选择；不使用答案表冒充运行数据 |
| B. 打通分析函数 | 封装单一输入输出，处理成功、部分结果和失败 | 一次由真实数据产生的结果及可回查证据 | 缺引用能力先补追溯；模型失败明确显示失败 |
| C. 完成最小应用 | 选择案例、启动分析、状态、结果、证据详情、反馈 | 从用户输入到核查的真实操作流程 | 不以静态截图或预填正确答案代替工作应用 |
| D. 执行测试 | 运行约 8 项功能、诊断、证据与失败检查 | 预期、实际、通过／失败、截图或运行记录 | 保留失败结果，修正错误后记录复测 |
| E. 可复现交付与 PPT | 固定依赖，编写数据和启动说明，整理真实截图与测试 | 仓库、可启动应用、约 10 页 PPT | 未测项目明确标注；不把计划写成成果 |

数据首先取小范围，但不能任意截断已有算法需要的参考数据。若方法使用全天基线，就保留所需数据，并明确这是离线分析，不能声称实时部署效果。可以先测试一例；第二例用于检查案例切换与硬编码，实际数量由可获取数据决定。

模型选择及调用预算在 A 阶段固定，记录具体模型、版本或可用标识、参数和运行时间。没有有效模型调用时可以开发界面，但不能将规则输出或缓存报告冒充本次实时 AI 分析。回放功能如保留，应明确标成回放。

## 6. 约 8 项测试及评价

| 编号 | 测试 | 检查内容与预期 |
|---|---|---|
| T1 | 真实案例 A 完整流程 | 实际执行并得到结果；用隔离答案评价诊断，逐项检查引用。诊断错误照实记录 |
| T2 | 切换到真实案例 B | 无需改代码，输入与证据正确切换，没有沿用 A 的缓存或人类反馈 |
| T3 | 时间与组件匹配 | 用可人工核算的样例检查秒／毫秒、时区和组件对应；不把其他窗口记录混入 |
| T4 | 证据回查 | 展示的每个引用均能回到正确原始记录；检查计算值和陈述是否得到支持 |
| T5 | 人类核查 | 拒绝或标记待核查并填写理由，界面明确保存于当前会话且关联正确运行 |
| T6 | 缺少部分数据 | 在受控副本中移除数据，清除相关缓存；说明缺失，不虚构该类证据。其余结论按剩余证据判断 |
| T7 | 无效引用 | 向输出校验器提供不存在的证据 ID，系统拦截或标记，不能显示为已核实证据 |
| T8 | 模型调用失败 | 模拟超时／连接错误，区分失败与无故障，不展示旧结果为新结论；提供可理解的错误状态 |

这是约 8 项测试，不是 8 个独立真实事故。T6–T8 是人为控制的测试，不能包装成数据集天然包含的故障。已知答案的开发案例不能同时作为未见案例的泛化证明。

评价分开报告：

1. **流程可用性：**哪些案例完成、哪些失败，用户是否能核查与反馈。
2. **诊断正确性：**依据题目要求的字段和官方评分器报告实际结果；缺失或未解决的必答字段仍计为未答对。不承诺提升原论文结果。
3. **证据质量：**逐条记录引用是否可解析、范围是否正确、陈述是否有支持。“引用存在”与“诊断正确”分别计量。
4. **异常行为：**缺数据和模型失败时是否如实显示状态。
5. **运行开销：**记录实际延迟与可获取的调用用量，不沿用未经验证的固定成本或速度承诺。

初始测试中“所有显示的引用均可回查、没有伪造记录”是工程验收目标，不是已经实现的结果。小样本只证明所测试流程的表现，不足以证明真实生产效率或普遍诊断准确率。即使出现诊断失败，也应展示并解释，不能为了漂亮分数删除案例。

## 7. 交付清单与 10 页 PPT

按用户最新决定，GitHub 使用新建的 AutoTriager-CoDesign 私有仓库，专门承载本次作业。旧 AutoTriager 仓库保留为早期规划，不作为本次实现依据；新仓库 README 按当前范围编写。human-ai-co-work-flowdesign 仓库是另一篇学习文章的存放处，不作为课程应用源码仓库。实现阶段先核对远端变化再更新，避免覆盖其他工作。

仓库至少包含：应用入口、分析与数据读取模块、输出及证据检查、依赖文件、数据获取说明或许可允许的样本、测试与结果、README。按实际模块拆分，不追求文件数量。密钥留在本地配置；数据是否可再分发先检查许可，不能上传整个答案集到应用可检索路径。

应用可供老师审查不自动意味着必须部署公网。可以提供明确的本地启动流程；如课程另有在线地址要求，再补部署。

| 页码 | 本次 PPT 要回答的问题 | 必须依据什么 |
|---|---|---|
| 1 | 项目为谁解决什么问题，第一个 P1 是什么？ | 已确认的目标与范围；署名 Dahe Chen |
| 2 | 三个设计阶段怎样连接？ | 原设计及本次因作业要求作出的调整 |
| 3 | 人做什么、AI 做什么、用户怎样核查？ | 实际交互流程 |
| 4 | 应用各模块怎样连接？ | 实际实现的架构，不画未用组件 |
| 5 | 用了什么数据、已有方法和模型？ | 实际版本、来源链接和输入范围 |
| 6 | 应用是否真的能使用？ | 实际运行截图 |
| 7 | 一个结果如何回到证据？ | 一次完整真实运行及原始记录 |
| 8 | 人能怎样影响和核查结果？ | 核查与反馈操作截图 |
| 9 | 编码助手做了什么，人改了什么？ | 实际修改、审查理由、测试与仓库链接；如实写 Codex |
| 10 | 测了什么、哪里失败、下一步是什么？ | 实际测试表与至少一个困难或失败案例 |

先获得运行证据，再填写第 6–10 页。当前可以准备页面结构，不能预写通过率或伪造运行截图。

## 8. 导师与 reviewer 审查

| 可能被追问的问题 | 当前风险 | 计划中的应对 |
|---|---|---|
| 这只是把论文输出放到网页上吗？ | 缺少用户任务与核查操作就只剩包装 | 提供案例选择、证据回查及关联到本次分析的判断；评价这些交互是否完成 |
| AI 为什么必要？ | 数值计算和筛选可以由普通工具完成 | 工具计算，模型综合观察并解释不确定性；不声称已经证明 AI 优于规则 |
| 所谓证据是否只是复制标准答案？ | 使用归档预测或标签会导致泄漏 | 分析只读题目和原始遥测，答案由独立评价流程读取 |
| 复用了什么，自己实现了什么？ | 容易夸大原创性或复现程度 | 明列已有算法、适配修改、界面、证据回查和人类交互的边界 |
| 你证明了根因吗？ | 相关异常不能单独证明因果 | 输出候选解释，区分标签匹配与证据支持，不声称证明完整故障传播 |
| 八个测试能证明工业价值吗？ | 小样本且含受控变体 | 用于功能验收，明确不能推出生产效果；未来增加未见案例与用户验证 |
| 人类究竟做了什么？ | 只有“接受”按钮可能缺少实际核查 | 可以打开原始证据并记录理由；保留一次真实人工纠错或拒绝的过程 |
| 计划能否按时落地？ | 数据、依赖和模型可用性仍不明确 | 最先验证 A 阶段，不先做复杂界面；阻塞时如实报告并重新定范围 |

**最终判断：方向可继续；当前尚不具备作业完成证据。优先验证真实数据与现有方法能运行，再把最小交互与测试完成。暂不启动实现，等待本计划讨论。**
